## 1. Моя роль одной фразой

> «Я готовлю **источник знаний**, на который опирается вся система: собираю исторический материал, превращаю его в аккуратный PDF, а затем извлекаю и нарезаю текст на качественные фрагменты (чанки), пригодные для поиска. Если этот этап плохой — весь RAG отвечает плохо, какой бы умной ни была нейросеть.»

## 2. Что именно сделано

1. **Исследование и компиляция контента** про Римскую империю — 14 разделов, ~6000 слов, охватывающих все ключевые аспекты: политика (Республика, Принципат, право), армия, экономика и торговля, культура и инженерия, общество, религия, семья.
2. **Генерация PDF** на 11 страниц (титул + 10 страниц контента) с заголовками, нумерацией страниц и читаемой типографикой.
3. **Извлечение текста** из PDF и его **очистка** (нормализация).
4. **Чанкинг** — нарезка текста на перекрывающиеся фрагменты с учётом границ разделов.

## 3. Какие технологии и почему

| Технология | Зачем |
|---|---|
| **ReportLab** (Platypus) | Высокоуровневая генерация PDF: сам разбивает на страницы, переносит текст, держит единый стиль заголовков. Заголовки потом служат «границами разделов» для чанкинга и метками для цитат. |
| **pypdf** | Извлечение текста из PDF постранично — стандартный, лёгкий инструмент. |
| **Регулярные выражения (`re`)** | Чистка артефактов извлечения: переносы слов, футеры «Page N», лишние пробелы. |
| Хранение контента как **структуры данных Python** (а не сплошной строки) | Позволяет аккуратно стилизовать заголовки/абзацы и переиспользовать тот же контент. |

## 4. Как это работает (для слайда «механика»)

**Шаг A. PDF.** Контент лежит в `content.py` как список `(заголовок_раздела, [абзацы])`. Генератор проходит по ним и строит PDF:
```python
for title, paragraphs in SECTIONS:
    story.append(Paragraph(title, styles["SectionHeading"]))   # заголовок
    for para in paragraphs:
        story.append(Paragraph(para, styles["BodyJustified"]))  # абзацы
doc.build(story, onFirstPage=_footer, onLaterPages=_footer)
```

**Шаг B. Извлечение + очистка.**
```python
text = re.sub(r"-\n(\w)", r"\1", text)               # склеить «инже-\нерия» → «инженерия»
text = re.sub(r"(?im)^\s*Page\s+\d+\s*$", "", text)  # убрать футеры страниц
text = re.sub(r"[ \t]+", " ", text)                  # схлопнуть пробелы, сохранив переносы строк
```
Переносы строк специально **сохраняются** — по ним дальше находятся заголовки разделов.

**Шаг C. Чанкинг (главная идея этой части).** Две ступени:
1. **Section-aware** — сначала режем документ по нумерованным заголовкам, чтобы каждый чанк был тематически цельным и нёс метку своего раздела (для цитат).
2. **Overlapping word-windows** — внутри раздела набираем целые предложения до ~220 слов (макс. 350), затем следующий чанк начинается с «хвоста» предыдущего в **80 слов**.
```python
if current_words + len(sent.split()) > MAX_CHUNK_WORDS:
    flush(carry_overlap=True)     # закрываем чанк и переносим 80-словный хвост
```

## 5. Почему это важно (ценность для проекта)

- **«Garbage in — garbage out».** Качество ответов RAG в первую очередь определяется качеством источника и нарезки. Чистый текст и осмысленные чанки = точный поиск.
- **Перекрытие (overlap) сохраняет контекст.** Факт, который начинается в конце одного чанка и поясняется в начале следующего, не теряется на стыке.
- **Границы разделов = честные цитаты.** Поскольку каждый чанк помнит свой раздел, система потом может ссылаться на `[4. The Roman Military]` — ответы становятся проверяемыми.
- **Воспроизводимость.** PDF и чанки можно пересоздать одной командой — это не «магический» датасет, а прозрачный пайплайн.

## 6. Результат (цифры для слайда)

- PDF: **11 страниц**, ~21 КБ, 14 разделов, все 5 требуемых аспектов покрыты.
- Из PDF получается **28 чистых чанков** (преамбула титульной страницы отбрасывается — индексируется только содержательный текст).
- Параметры чанкинга: цель ~220 слов, перекрытие 80 слов (в рамках рекомендаций задания 300–800 слов / 50–100 overlap; уменьшили из-за плотного текста — это дало более резкие скоры поиска).

> «Я отдаю **список чистых чанков с метками разделов** Части 2, которая превращает их в векторы и строит поисковый индекс. Без качественных чанков её поиск был бы шумным.»

## 8. Вероятные вопросы (и ответы)

- **Почему не взяли готовый текст из интернета/Википедии?** — Нужен самодостаточный, контролируемый по качеству источник; так демонстрируется весь пайплайн от создания документа.
- **Почему чанки ~220 слов, а не 800?** — Текст очень плотный фактами; меньший размер дал более точные совпадения и аккуратные цитаты. Подбирали по метрикам (см. Часть 3).
- **Зачем перекрытие?** — Чтобы факты не «разрывались» на границе чанков.
- **Что было сложным?** — Артефакты извлечения PDF (переносы, футеры) и «шум» титульной страницы; решено регэкспами и отбрасыванием преамбулы до первого заголовка.
